## A 输入框与上下文

用户原话：“Commands `/` 和 `@` plugins / context files / other chats”。补充（2026-10-21）：Command 对应的是命令的注册和自定义，以及在输入框中添加上下文。

拆开后是三件事：

- **A1 选择命令**：输入 `/` 弹出命令列表。内置命令有深度搜索、读网页、总结会话、开支线，每个 Skill 也是一条命令。
- **A2 注册和自定义命令**：用户能增加自己的命令，或者修改内置命令的指令。现在命令只来自代码和 Skills，用户能做的只有新增 Skill。
- **A3 添加上下文**：`@` 一个插件、一个资料文件或另一个会话，作为这一轮的上下文。

用户答复（2026-10-21）：命令和 Skill 都保留，`@` 要能选会话和文件。阶段 9 起 `@` 还能选本会话工作区里的文件，本会话的 Skill 也出现在 `/` 列表里。

1. ~~自定义命令和 Skill 的区别~~（已答复：两者都保留）。现在的理解是：命令是“一段保存好的指令，选中就发送”；Skill 是“一套做事方法，助手判断需要时自己读”。如果两者合并成“带一个 `/` 名字的 Skill”，只需要维护一处。
2. 自定义命令在哪里编辑：定制页里的表单，还是工作区或 Drive 中的文件（例如 `commands/<名字>.md`）？
3. 命令是否需要参数（例如 `/翻译 英文`），还是只把输入框里的正文作为参数？
4. `@` 的上下文还要加什么：项目、网页链接？（工作区文件已加入）

## E Skills

原话只有“Skills”。来源是内置三个 Skill，再加上 Drive `GenseBot/Skills/<名字>/SKILL.md`。阶段 9 之前助手通过专门的 `skill_activate`、`skill_read` 工具读取；阶段 9 起这两个工具已删除，改为下面的做法。

补充（2026-10-21）：Skills 可以设计成让助手自己去读 Skill 的内容。有了工作区（F1），Skill 就是工作区里的普通文件，助手用通用的读文件工具去读，不再需要专门的 Skill 工具。Think 0.21 已经支持把 Skills 放进工作区的 `/workspace/.agents/skills` 下（`skillWorkspace` 选项）。之前没有用 Think 自带的 Skills，原因见路线图 2 的“L2 Skills”，所以这次可能仍然自己往工作区里放文件。

用户答复（2026-10-21）：“Skills 一部分是只读的挂载，一部分是可以读写的，对自己生效。”已按此实现（阶段 9）：

- 设置里启用的 Skill（内置和 Drive）挂载在每个会话的 `/skills`，只读，Drive 中改了 `SKILL.md` 后下一轮重新挂载。
- 助手可以在 `/workspace/skills/<名字>/SKILL.md` 新建或修改 Skill，只对这个会话生效；同名时覆盖共享的那份。
- 助手用通用的 `read` 工具读取 Skill，系统提示里列出每个 Skill 的路径。

## F 会话工作区（新增 G11）

原话（2026-10-21）：“每一个对话都要有 filesystem。也可以不只是 filesystem，可以是一个小的 sandbox。Sandbox for every chat。”

理解：每个会话有一个属于自己的目录，助手可以在里面读写文件、整理中间结果，把 Skills、附件、支线总结和生成的产物都放在这里。用户也能看到这个目录。

可行性（2026-10-21 查证）：

- **文件系统，Free 计划可以做。** Think 0.21 本来就给每个会话一个 `workspace`：由 `@cloudflare/computer`（预览版）实现，存在会话 Durable Object 自己的 SQLite 里，接口类似 `node:fs/promises`，并自带 `read`、`ls`、`find`、`grep`、`write`、`edit`、`delete` 工具。我们目前在 `worker/chat.ts` 中隐藏了这些工具。单个工作区上限约 10 GB，与 DO 共用存储。
- **运行命令或代码，Free 计划做不到。** `@cloudflare/computer` 有三种执行后端：容器（Cloudflare Containers）、Worker 内的 shell、隔离的 JavaScript 运行时。后两种需要 Worker Loader，容器也需要付费计划。这和 Codemode、Skill 脚本是同一个限制（ADR-0003）。

用户答复（2026-10-21）：“先提供文件系统吧，每一个会话一个。分支和 branch 后续会改造一下，设计为 tree-based 的，一个会话就是一个 tree。只有 tree 的主干才能修改文件系统，branch 能不能以类似 worktree 的形式存在呢？”

已实现（阶段 9）：每个会话一个工作区，会话顶栏的文件夹按钮打开文件面板（浏览、预览、下载、删除；手机上全屏）。分支到新会话时复制主线 `/workspace` 的文件（上限 16 MB），这是树形会话之前的过渡做法。设想见路线图 2 的“L0-6 会话工作区”。
